# Secrets

Every secret and deploy setting the app needs, and where each one lives. To put
them in place, follow [Set up a deployment](../how-to/set-up-a-deployment.md).

Five places hold them and none can read another's, so two values are
deliberately stored twice. `OUTBOX_DRAIN_SECRET` in particular lives in both the
Edge Function environment and in Vault, because Postgres is the sender and the
function is the receiver.

## Edge Function environment

Set with `supabase secrets set`. They take effect without a redeploy.

- **`TELEGRAM_BOT_TOKEN`**: from BotFather. The `telegram` and `outbox-drain`
  functions both send with it.
- **`TELEGRAM_WEBHOOK_SECRET`**: generated by you and handed to Telegram's
  `setWebhook`. Telegram echoes it in `X-Telegram-Bot-Api-Secret-Token` on every
  update and the function compares it in constant time. It is not derived from
  the bot token, and it is the only proof a request came from Telegram.
- **`OUTBOX_DRAIN_SECRET`**: the `X-Outbox-Secret` that pg_cron sends to
  `outbox-drain`. Must equal the Vault copy.
- **`DEEPSEEK_API_KEY`**: used by `parse-assist` for **Read with AI**. Without
  it the function returns 501 and the button says so. See
  [Menu parsing](../explanation/menu-parsing.md).
- **`LUNCH_DB_POOL_URL`**: the transaction-mode pooler URI (port 6543). Absent,
  the bot falls back to `SUPABASE_DB_URL`, which is fine at today's traffic. The
  name cannot start with `SUPABASE_`, a prefix the platform reserves.

`SUPABASE_URL`, `SUPABASE_DB_URL`, `SUPABASE_SECRET_KEYS` and
`SUPABASE_PUBLISHABLE_KEYS` are injected automatically and must not be set by hand.

## Vault

The hourly tick and the outbox drain run inside Postgres, which cannot read Edge
Function environment variables. They read `project_url`, `publishable_key` and
`outbox_drain_secret` from Vault instead.

Not hardcoded in a migration: migrations are committed, and Vault is encrypted at
rest. Until these exist the drain logs a NOTICE with the pending count each minute
and sends nothing, which is recoverable. An unsent message is; an unrecorded one
is not.

## `public.org_webhook_secrets`

The SePay webhook key is **not** a Supabase secret. It belongs to one office,
because the `sepay` endpoint routes by the account number in the payload, and a
single shared key would let any office post payments into any other. An office
with no row refuses every delivery. [Connect SePay](../how-to/connect-sepay.md)
covers generating, storing and rotating it.

## GitHub

Under *Settings > Secrets and variables > Actions*.

- **`SUPABASE_ACCESS_TOKEN`** (secret): a personal access token that lets the
  deploy workflow run `supabase functions deploy`.
- **`CLOUDFLARE_API_TOKEN`** (secret): from the *Edit Cloudflare Workers* template.
- **`CLOUDFLARE_ACCOUNT_ID`** (secret): from the Cloudflare dashboard.
- **`VITE_*`** (variables): repository **variables**, not secrets, on purpose.
  Vite inlines them into the bundle, so they are public the moment anyone loads
  the page, and masking them in a CI log would only give false assurance. They
  are still required: without the two Supabase ones the build succeeds and ships
  an app that reports a config error to every visitor. `VITE_TELEGRAM_BOT` is
  optional; absent, the preferences screen shows the raw `/start` command
  instead of a `t.me` link.

A secret behind the `VITE_` prefix is a full compromise. See the invariants in
[Database](database.md#invariants).
